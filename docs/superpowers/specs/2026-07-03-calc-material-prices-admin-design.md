# Цены материалов калькулятора в админке — дизайн

**Дата:** 2026-07-03
**Ветка:** feature/light-design-system (PR #10) или отдельная — по решению при планировании

## Проблема

Цены сырья калькулятора (`EVA = 380 ₽/кг`, `ПВД = 360 ₽/кг`) захардкожены в
`www/includes/calculator.php` (`private $materialPrices`). При изменении цен на
сырьё расчёт устаревает, а поправить его может только разработчик через код.
Нужно, чтобы цены материалов правил менеджер/владелец через админку.

## Цель

Вынести цены материалов калькулятора (EVA и ПВД, ₽/кг) в редактируемые из
админ-панели настройки, хранящиеся в БД. Поведение калькулятора при этом не
меняется, пока значения не отредактированы (текущие 380/360 остаются
дефолтами).

## Область (scope)

**Входит:**
- Цена EVA (₽/кг) — редактируется.
- Цена ПВД (₽/кг) — редактируется.

**Не входит (осознанно, YAGNI):**
- Физические константы формулы (плотность плёнки 0.92, вес молнии 6.4 г/м,
  вес бегунка 0.25 г) — остаются в коде.
- Пороги/проценты скидок — уже сведены с тарифами витрины
  (`WHOLESALE_TIERS`), отдельно не выносим.
- Добавление новых материалов помимо EVA/ПВД.

## Архитектура

Три слоя с чёткими границами:

### 1. Хранилище — таблица `settings` (key-value)

Универсальная таблица «ключ-значение», чтобы в будущем класть туда и другие
настройки без новых миграций структуры.

```sql
-- db/migrations/2026-07-03-settings.sql
CREATE TABLE IF NOT EXISTS `settings` (
  `setting_key`   VARCHAR(64)  NOT NULL,
  `setting_value` VARCHAR(255) NOT NULL,
  `updated_at`    TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`setting_key`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

INSERT INTO `settings` (`setting_key`, `setting_value`) VALUES
  ('calc_price_eva', '380'),
  ('calc_price_pvd', '360')
ON DUPLICATE KEY UPDATE `setting_key` = `setting_key`;  -- идемпотентно
```

Ключи: `calc_price_eva`, `calc_price_pvd`. Значения — строки, интерпретируются
как float на чтении.

### 2. Чтение — `www/includes/app_settings.php`

Новый модуль, отвечает только за доступ к настройкам:

- `get_setting(string $key, $default)` — читает значение из БД с кэшем на
  запрос (статический массив). Если таблицы нет (миграция не накатана) или
  строки нет → возвращает `$default`. Ошибку БД глушим до дефолта, чтобы сайт
  не падал при отставшей схеме.
- `set_setting(string $key, string $value)` — UPSERT (INSERT … ON DUPLICATE
  KEY UPDATE), сбрасывает кэш ключа.
- `calc_material_prices(array $overrides = []): array` — **чистая функция**:
  мёржит переданные значения поверх дефолтов `['EVA'=>380.0,'ПВД'=>360.0]`,
  приводит к float, отбрасывает неположительные. Тестируется без БД.

`Calculator` (в `www/includes/calculator.php`):
- Конструктор принимает необязательный `array $materialPrices = null`. Если
  передан — используется он (для тестов и явной инъекции); если нет — цены
  берутся из `calc_material_prices([...get_setting...])`.
- Дефолтный фолбэк 380/360 сохраняется внутри `calc_material_prices`, так что
  при отсутствии настроек поведение идентично текущему.

### 3. Админка — `www/admin/settings.php`

Дополняем существующую заглушку:

- **Доступ на просмотр:** уже гейтится `view_settings` через
  `checkPageAccess('settings.php')` (superadmin + admin).
- **Сохранение (POST):** `requirePermission('edit_settings')` — только
  superadmin (по аналогии с `edit_users`). admin видит цены, но не меняет.
- **Форма:** два числовых поля — «EVA, ₽/кг» и «ПВД, ₽/кг», предзаполнены
  текущими значениями из БД.
- **CSRF:** токен как в других админ-формах (тот же механизм, что в
  users.php/leads.php).
- **Валидация:** каждое значение — число `> 0` и `<= 100000` (разумный
  потолок от опечаток). При ошибке — сообщение, значения не сохраняются,
  форма показывает введённое.
- **Успех:** флеш-сообщение «Настройки сохранены», перерисовка с новыми
  значениями.
- **Навигация:** пункт «Настройки» в меню админки (если ещё не выведен).

## Поток данных

```
Админ (superadmin) → форма settings.php → POST (CSRF+valid) → set_setting()
                                                                    ↓
                                                              таблица settings
                                                                    ↓
Клиент → калькулятор JS → api.php?action=calculate → new Calculator()
        → calc_material_prices(get_setting(...)) → calculatePrice() → цена
```

## Обработка ошибок

- Миграция не накатана / нет коннекта к БД при чтении → `get_setting`
  возвращает дефолт, калькулятор работает на 380/360. Логируем в error_log,
  но не падаем.
- Невалидный ввод в форме → не сохраняем, показываем ошибку рядом с полем.
- Отсутствие прав на сохранение → 403 через `requirePermission`.

## Тестирование (PHPUnit, стиль проекта — чистые функции без БД)

Новый `www/tests/CalculatorSettingsTest.php`:
1. `calc_material_prices([])` возвращает дефолты `['EVA'=>380.0,'ПВД'=>360.0]`.
2. `calc_material_prices(['EVA'=>500])` → EVA=500.0, ПВД=360.0 (мёрж поверх
   дефолта).
3. `calc_material_prices(['EVA'=>0,'ПВД'=>-5])` → неположительные отброшены,
   вернулись дефолты.
4. `new Calculator(['EVA'=>500,'ПВД'=>400])` → `calculatePrice(...)` для EVA
   считает по 500 ₽/кг (проверка инъекции без БД).

Тест на скидки не требуется (не меняли; калькулятор-теста нет и не заводим
сверх нужного).
